# Syntax Migration Inventory

## Purpose

Syntax 06A M1 provides a deterministic, read-only inventory of legacy ZR syntax before any parser,
compiler, CLI, or language-server migration action is allowed. The inventory is the common input for
the 06A M2 edit planner and M3 dry run; it does not rewrite a source file, approve an edit, or change
the formal language accepted by the frontend.

## Input Boundary

The scanner reads Git-tracked candidates under `tests`, `examples`, `docs`, `extensions`,
`zr_vm_lib_*`, and `zr_vm_library`. ZR files are lexed directly. Test and extension host files are
considered only for string literals that are explicitly assigned or passed as ZR source input; this
prevents C format strings, generated C source, and diagnostics text from being mistaken for ZR syntax.
Documentation contributes only fenced `zr` snippets.

The report retains every selected candidate exactly once. Binary artifacts, historical plans,
third-party sources, expected-diagnostic fixtures, migration self-fixtures, and generated output are
written to `exclusions` with a stable reason. They are not silently skipped. Artifact formats are never
text-patched by this tool.

## Classification Contract

Every finding records its repo-relative file, source kind, exact line and column range, legacy form,
classification, target plan, and stable reason. The only classifications are:

- `machineApplicable`: the target syntax is already promoted and the local structural contract is
  unambiguous.
- `maybeIncorrect`: reserved for a mechanically possible edit whose semantic proof is insufficient.
- `requiresReview`: migration needs binding, ownership, or other source-context review.
- `blocked`: the source form is recognized but has no valid migration proposal.
- `targetNotPromoted`: the target form belongs to a downstream plan that has not passed its promotion
  gate.

Forms owned by Syntax 08, 10, 11, 12, 13, or 14 remain `targetNotPromoted` even if a textual rewrite
looks obvious. M1 therefore cannot use the inventory to produce a quick fix or a workspace edit.

## Invocation And Output

Run the repository report without modifying input files:

```text
python scripts/syntax_migration_inventory.py --root . --format json --output migration-inventory.json
python scripts/syntax_migration_inventory.py --root . --format text
```

The JSON schema contains `schemaVersion`, `scannerVersion`, `selectedRoots`, all `scannedFiles`, all
`exclusions`, sorted `findings`, `classificationCounts`, `targetPlanCounts`, and `unknownCount`. Paths
are relative to the selected root, so a report generated by the Windows host and WSL build hosts has
the same bytes when their tracked source state is identical.

`tests/fixtures/syntax_migration_inventory/expected/inventory.json` freezes the synthetic lexical and
classification contract. `repository-inventory.json` freezes the reviewed repository baseline. The
test suite compares both byte-for-byte and verifies that no source artifact is simultaneously scanned
and excluded.

## Constraints And Follow-up

The scanner is deliberately an inventory frontend rather than a parser adapter. It does not infer
property pairing, generic constructor binding, ownership escape safety, dynamic reflection targets, or
artifact compatibility. Those decisions remain with M2 and with the target-plan promotion gates. A new
legacy-looking form must either receive a stable classification and target owner or remain visible as a
`blocked` finding; it must not be hidden by a filename, diagnostic text, or raw-text heuristic.

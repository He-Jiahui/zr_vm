# ExecBC pattern lowering and generated fusion

## Purpose

This module describes the parser-owned projection contract for combining two
adjacent ExecIR operations into one fixed-width ExecBC word.  ExecIR remains
the only semantic source.  The fusion plan is immutable with respect to the
input function and carries only scalar IDs, hashes, and bounded arrays, so a
runtime handler can use it without retaining parser or runtime pointers.

## Schema and generated metadata

`execbc_patterns.def` is the single source for the six initial rules:

1. `LOAD_ADD_INT`
2. `COMPARE_BRANCH_INT`
3. `INDEX_LOAD_STORE`
4. `BINDING_CALL`
5. `INCREMENT_LOOP_BRANCH`
6. `CALL_RETURN`

The Python generator emits `execbc_fusion_patterns_generated.h`.  The generated
header contains the ordered X-macro rows and the schema count; it has no
runtime behavior.  `--check` compares generated bytes with the checked-in
header and fails when the generated artifact is stale.  The historical
`execbc_fusion_patterns.def` path is a local include shim only; it cannot add
or reorder rows.

## Fixed-width output and side tables

`SZrExecBcFusionInstruction` is an alias of the existing `SZrInstruction`, and
the header has a compile-time size assertion.  Existing instruction codes are
not renumbered: generated fusion codes start at `ZR_INSTRUCTION_ENUM(ENUM_MAX)`.
The 16-bit `operandExtra` stores the side-entry index.  A side entry records
both source instruction IDs, source/resume IDs, all operands (up to the bounded
contract maximum), explicit head/tail operand partitions, every branch successor
and its projected PC, binding row,
guard mask, and contract witnesses.  Conditional ExecIR branches retain both
explicit edges (taken and fall-through); the legacy singular target fields
mirror edge zero.  If a window needs more operands or exceeds side-table or
code budgets, it remains in the original sequence and a structured fallback
reason is recorded; no value is truncated.

The source map emits two records per fused window, preserving original source
and resume identity (deopt/state-map resume IDs are preferred, with the
instruction ID as a stable fallback).  Branch block IDs are resolved only
after the complete window scan, so a target that lands in a fused pair points
at the pair's output PC.

## Matching and safety boundaries

The matcher scans each function once with a non-recursive two-instruction
window.  A candidate must have matching opcodes, one block, adjacent IDs,
compatible type tokens, a directly connected effect chain, a single use of the
intermediate result, and any rule-specific layout/binding/branch proof.  A
debug, safepoint, exception, or reentrant boundary is accepted only when the
rule declares that exact boundary and carries `PRESERVE_BOUNDARY`; its mask is
retained in the side entry for the eventual handler.  An unrepresented
boundary causes a structured fallback.

No native/getter/member name lookup is performed by fusion.  Binding rules
consume the already-resolved binding row produced by static-binding facts.
When a facts table is supplied through `SZrExecBcPatternOptions`, it is
validated before generation and may authorize row index zero (the first row
is a valid zero-based table index).  Without that explicit witness, zero is
treated as unpublished and the call window falls back; this prevents an
unknown/native call from becoming a fast path accidentally.  Index and
null/overflow semantics remain in the original operation handlers;
fusion only records a projection and never claims a new semantic shortcut.

## Budgets, fallback, and invalidation

`SZrExecBcPatternOptions` controls enabled rules, maximum fused windows,
side-entry/fallback counts, code bytes, minimum dispatch benefit, generation,
signature/module/layout witnesses, and boundary policy.  A failed precondition
does not fail the whole projection: the original operation is emitted and the
specific `EZrExecBcFusionFallbackReason` is retained.  Contract mismatch,
stale generation, malformed input, and sealed-function violations fail before
the output plan replaces an existing plan.

The plan stores an input hash and pattern-schema hash.  `CheckValidity` compares
generation, signature, module/layout witnesses, and a fresh input hash.  A
caller can invalidate a plan explicitly; invalidation restores the original
fixed-width sequence, clears derived side/source/fallback arrays, marks the
plan invalid, and records the reason.  No stale generated handler is silently
reused.

## Ownership and lifecycle

`Init` is safe on a zeroed record.  `Free` is idempotent and frees arrays only
when the storage tag and count/capacity invariants are trusted, which keeps
partially initialized or diagnostic paths safe.  Build is transactional: a
candidate plan is fully generated before the caller's existing output is
released.  The source ExecIR and all caller-owned option fields remain
unchanged.

## Test coverage

`tests/parser/test_ssa_generated_fusion.c` covers all six positive patterns,
debug/type/effect/layout/binding failures, explicit static-binding authorization
of zero-based row zero, wide side operands, long branch targets, budget
fallback, fixed-width size, source/resume mapping, branch remapping,
deterministic hash and bytes, output-wrapper selection, generation
invalidation, contract mismatch, transactional output preservation, and the
empty-function/partial-lifecycle case.  The focused fixture is
compiled against the core ExecIR model and can be run independently of the
large legacy test graph.

## Out of scope

This stage does not rewrite the legacy quickening compiler or core dispatch
table, does not emit executable handlers, and does not mutate `SZrExecIrFunction`.
CTest registration and integration into the shared dispatch build remain the
responsibility of the parent 03.04 integration stage.

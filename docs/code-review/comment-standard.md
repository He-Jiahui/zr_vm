# 调用链审查与注释规范

## 范围与清单

审查首方产品代码、测试、脚本、构建配置和人工编写的测试样例。第三方子模块、依赖副本、生成产物、二进制文件、锁文件和纯快照数据不作为注释对象。JSON 等不允许注释的格式仍需审查其配置或消费关系；结论写入台账或相关文档。归档目录中的首方源码也在范围内，是否仍参与构建必须逐文件核对当前构建配置。

以当前工作树中的已跟踪及未跟踪文件建立文件清单；每批开始与全仓结束时重新扫描，新增首方文件不得遗漏。记录文件归属、是否由其他活跃会话修改，以及审查状态。工作区原有差异不属于本任务，不能随注释提交。

`scripts/code_review_inventory.py sync` 根据 Git 文件列表更新 `inventory.tsv`，用 `sha256` 记录审查时的文件内容；内容变化会将该行重置为 `pending`，未变化则保留既有 `status` 和 `note`。`check` 核对清单是否与当前工作树一致，最终验收使用 `check --require-complete`，还会核对已审文件至少有一条格式正确的逐单元台账记录。文件级状态只用 `pending` 与 `reviewed`，仅在该文件的全部适用单元均有台账结论后改为 `reviewed`；脚本无法单凭清单证明没有遗漏函数，仍需独立审查者核对定义与台账。活跃会话的文件归属记录在会话协调说明与清单 `note` 中；归属释放前可只读审查，不写注释。

审查单元包括每个函数、可调用宏、公开接口、结构或类型定义，以及承载独立契约的全局状态。逐个阅读函数内的语句块；当某个块有跨层意图、隐含不变量或具体风险时，单独登记该块。普通局部控制块的审查结论随所属函数记录，不按花括号数量制造重复台账行。
JavaScript/TypeScript 的箭头函数、对象方法、事件处理器和 Promise 回调都属于可调用单元；即使只是 `map`、`filter`、`find`、`some` 的简短谓词，也须逐个登记，确属局部纯谓词时可选 `no-comment` 并说明理由。测试中作为字符串注入后实际执行的函数也须登记；普通测试数据字符串中的函数样文本不算代码。多个回调写在同一源码行时仍按可调用单元分别登记，审阅时以语法树清点数量并核对各自调用点。

## 从调用方还原意图

1. 从声明、实现和构建入口定位单元，搜索全仓直接调用及数据结构的构造、读写、转移、释放位置。
2. 追踪函数指针、回调注册、宏展开、生成代码、命令或测试入口，以及 C、Rust、TypeScript、WASM 等跨语言边界。文本搜索无结果不能证明死代码。
3. 向上追到用户可观察入口，向下查关键依赖和失败路径；核对调用前提、结果归属、有效期、线程/异步顺序及失败后状态。
4. 用当前源码、构建配置和测试相互印证。历史计划和模块文档只作线索；与当前调用路径矛盾时，先记录疑点再下结论。
5. 对每个单元给出明确结论：需要注释、无需注释、待核实或已证实缺陷。无法确定的契约不能写成事实。

## 注释内容和位置

新注释以中文为主，保留 API 名、协议名与 `TODO:`、`BUG:` 标签。已有准确注释无需机械重写。注释解释职责及调用目的，按需补充前置条件、资源所有权与有效期、失败语义、线程/时序限制、设计取舍和调用链意图；不逐句复述实现，也不在每处硬编码完整调用方清单。

- C 公开声明使用 `/** ... */` Doxygen；`@brief` 说明对调用方的作用，`@pre`、`@return`、`@note` 仅在存在相应契约时使用。调用约束优先写在声明处，内部实现只解释非显然的原因或不变量。
- TypeScript/JavaScript 导出接口使用 JSDoc；Rust 公开接口使用 `///`，不安全边界按 Rust 惯例使用 `// SAFETY:`；Python、脚本和 CMake 使用各自语言的行注释。
- 数据结构说明状态不变量、字段之间的关系、所有权或 ABI 限制。关键语句块说明为何必须采取该顺序、检查或回退。测试注释说明场景与防止的退化，而非重复断言。
- 示例和快照若会因注释改变解析或期望结果，只在台账中记录结论，不为追求注释数量修改它们。

`BUG:` 仅用于已复现，或经完整可达调用路径证明的缺陷；同处写明触发条件、可观察影响及复现测试或证据。`TODO:` 用于仍需确认的契约或风险；同处写明疑点、已知证据和下一步核查入口。推测性缺陷不得标为 `BUG:`。标签放在最贴近问题的源码或文档处，并在台账中保留完整证据。发现问题不在本任务内改变程序行为。

## 台账格式

每个功能模块在 `coverage/` 放置 UTF-8 TSV，首行固定为：

`file	unit	kind	callers	intent	constraints	evidence	decision	reason`

`file` 用仓库相对路径；`unit` 用可检索的限定名，语句块另附所属函数和用途；`kind` 标识函数、类型、宏、状态或语句块。`callers` 列列出直接调用者及已查明的间接入口；公共 API 至少给出有代表性的具体调用位置，或说明核查后的仓内调用范围（例如仅有内部调用、仓内未发现调用），不能只写“parser”“runtime”等泛称。配置、测试或 CI 流程中的相邻步骤只有实际读取或执行本单元时才列为调用者；只是前置条件或后续验收的步骤写入约束与证据，不冒充调用点。仓内未发现调用时记录已检查的仓内入口；仓内搜索不能排除仓外消费者。新批次及返工批次的 `evidence` 列使用当前实现、测试、构建或复现的仓库相对 `path:line` 锚点；每个锚点必须指向当前工作树中的非空、与结论直接相关的行，不能指向空行、无关括号或以纯叙述代替路径。旧批次中尚有路径或叙述式证据，随对应模块复审迁移，不能直接宣称已满足此项锚点规则。`decision` 只使用 `commented`、`no-comment`、`TODO`、`BUG`。`no-comment` 必须在 `reason` 中说明为何现有名称或注释已足够。字段内用分号分隔多个值，不插入制表符或换行。

每个新审或返工模块结束时核对台账与定义清单，确认没有未登记的审查单元；运行 `python scripts/code_review_inventory.py check-batch docs/code-review/coverage/<模块>.tsv` 检查九列、重复单元及 `evidence` 锚点的存在和非空，再逐条核对锚点与结论的语义对应；`check-batch` 不验证调用方向，必须逐条核对 `callers` 的实际上游调用、行号与目的，定义、声明、相邻断言不能冒充调用点，并复核注释是否仍与当前工作树一致。若模块文档因此失真，依照文档现有的 `related_code`、`implementation_files`、`plan_sources` 和 `tests` 头部同步修正。

源码新增注释会移动其他模块台账中的行号。提交前按本批改动路径搜索 `coverage/` 的反向引用，复核已审批次的 `callers`、`evidence` 是否仍指向同一调用与语句；对已使用规范锚点的批次重跑 `check-batch`，并在本次提交中修正漂移。旧批次的范围、符号名或叙述式证据须随其模块返工迁移，不能以非空行号替代语义复核。

## 分工、验证与提交

验证命令必须显式传入本批目标路径，并确认实际处理的文件或台账记录数。无参数、未处理目标或零条审查记录的检查不得作为通过证据；验证脚本应将这类调用视为失败。保存执行命令、退出码和实际检查范围，不能仅依据无输出或退出码零宣称验证通过。执行返回 `session_id` 或 `cell_id` 时应继续等待终态结果；“仍在运行”或仅有中间输出不能作为通过证据。

多位 subagents 可并行进行只读调用链调查；写注释时每个文件只有一名负责者。独立 reviewer 核对注释是否从当前调用证据得出，是否遗漏单元或误用问题标签。活跃 SSA、LSP 等会话拥有的文件只读审查，待文件归属释放后再写入。

每个功能模块单独验收和提交。提交前运行 `git diff --cached --check`，检查暂存文件与完整差异，执行受影响模块的现有构建和测试，并与修改前基线比较。只暂存本任务的注释、台账及必要文档更正；不能安全拆分的原有差异继续延后。注释工作不添加只重复实现的测试，也不把已存在的测试失败描述为本任务修复成果。


## 证据封存与独立复查补充

本节适用于后续审查批次，与前述规范共同执行。

本补充不改变用户已授权的任务范围。当前源码、当前构建/测试证据及用户有效指令优先；历史报告与协调记录只证明其记录时点和范围。本批正常的只读审查、私有候选准备及已授权独立路径工作可继续；仅对实际重叠的文件归属、索引事务或新锁进行有限协调，不新增普遍审批或每步重新 ACK 的流程。

### 审查结论与阅读证据

文件全文读取、搜索命中数量、正确的 hash、语法检查和补丁可应用性，各自只能证明对应的机械事实。逐单元结论还必须由实际调用上下文支持。独立 reviewer 必须自行阅读相应正文及调用位置，不能将生产者报告的通过结果转述为独立验证。

正式台账中的 `commented` 表示当前共享源码确有经核实的准确注释；未应用的候选只在私有候选台账或 manifest 中记录提案状态、目标版本及“尚未应用”，不得据此推进正式单元或文件的完成信用。`no-comment` 必须解释为什么已有命名、局部条件或准确旧注释足以表达已核实的意图。`TODO` 和 `BUG` 均须由当前源码及实际调用证据支持；无法确认的契约保留 `TODO` 与具体下一核查入口，不要求将所有疑点彻底证明后才交付已审范围。不能将所有 constraints 填入同一段通用说明。正式九列台账仅允许 `commented`、`no-comment`、`TODO`、`BUG`，不新增 decision 值。`PENDING` 可用于私有批次或协调状态；正式 inventory 仍只使用小写 `pending` / `reviewed`，不能将批次状态冒充逐单元结论。

### 定义与调用的身份

直接调用、声明、定义、宏引用、函数指针注册、实际派发和同名静态函数必须分别记录。实际调用或注册入口使用仓库相对的完整 `path:line`，定义地址放 evidence。仓内未发现调用时，保留原规范允许的已检查入口及范围说明；这些检索范围不是调用点，也不证明没有仓外消费者。公共 API 的代表调用位置仍按原规范执行。同名静态符号须按定义及翻译单元归属分辨；其他翻译单元中同名符号的命中，不计为当前单元的调用。注入测试字符串内的函数另按执行入口登记。

本批若以原始正文摘要、候选重建或补丁校验作为交付证据，须在 manifest 列明文件、单元与版本范围，并按下述规则留存。语义审查仍须实际阅读适用单元及与结论相关的调用、依赖和失败路径；不额外要求对无关 helper 递归生成 raw hash 收据，不能在达到声明范围后不断扩展无关证据门槛。

正文边界必须覆盖含签名的完整函数。多行签名的 `{` 所在行不是函数结尾。收据明确使用 `sha256(b''.join(Path(file).read_bytes().splitlines(keepends=True)[start_line-1:end_line]))`，记录含起止行、原换行及末尾换行；不能以未声明的 LF 规范化 hash 冒充原始字节 hash。字段或语句块使用同样的明确范围规则。

### 注释语义与问题标签

类型、枚举或函数名属于搜索线索，不能直接替代该调用点的用途解释。可以让同一函数内多个等价调用共享一个具体契约，但必须列出所有对应位置并说明其在调用链中的实际角色；代码原文加分类模板不等于用途解释。所有权与生命周期必须按所用对象分别核查，不给纯枚举赋值套用指针或 context 生命周期。

测试注释与台账只描述实际构造和断言的场景。区间上下界、离散段、fact kind、溢出标志和诊断严重性分别核对；不得宣称未断言的覆盖。`WARNING` 不能写成错误诊断，`mayOverflow` 不能写成已发生溢出，筛选条件未检查 `isResolved` 时不能加入“已解析”前提。

分配失败标签要写清真正会分配的步骤。已分配且仍有容量时的首次 Add 不会触发扩容；相应增长 OOM 风险应标在达到容量后的路径。完整静态可达链可以证明 BUG，但它不授予故障注入或运行时验证信用。尚未证明的上游约束、回调实现或失败清理写 TODO，并列出已知条件和下一核查入口。

### 候选源码与字节校验

候选源码在私有目录重建，保留每个源文件的原始字节和行结束方式，禁止借准备候选修改共享源码。收据分别保存 raw source SHA、candidate SHA、patch SHA、真正 Git HEAD 和必要依赖 SHA；不能把头文件 SHA 填进 HEAD 字段。补丁的 current-tree check 必须针对本次的当前文件执行；隔离副本通过不替代当前工作树通过。涉及 autocrlf 时记录实际仓库设置与检查参数，并验证候选的非注释 token、字符串及预处理约束。

token 一致仅表示对应的静态词法对比通过，不表示已有测试运行、构建完成或缺陷复现。运行时与构建证据分别记录实际命令、源码快照、终态退出码和未完成范围；未启动或超时的过程保留 UNKNOWN。是否需运行探针或现有测试按原规范、本批风险及已授权验证范围确定，不为静态审查默认新增无限的运行时验证门槛。

### 冻结、修订与提交流程

每批审查文件名按不可变版本命名。发出 FROZEN/STOP 后不覆盖原件；修订使用新版本名，并在 manifest 指向父版本的实际 SHA 和逐字段 delta。路径后缀拼接使用显式文件名，避免 `.with_suffix()` 将版本段误当扩展名。误覆盖事件保留现状及事实；没有原始字节时不得以重建内容声称恢复历史原件。

正常索引事务前重新观察 HEAD、raw source、index、lock、暂存条目与实际文件归属。此前 owner ACK 证明其对应时点与约定范围，不能单独证明当前 HEAD、源码、index 或 lock 未变。复核当前状态及 ACK/归属约定仍有效且无冲突时，沿用已有授权；出现实际冲突或新锁时只协调受影响的边界，不阻止无冲突的独立工作。保留新的锁并与实际 owner 有限协调，不删除锁、不另设 index、不处理外来暂存条目。按模块列出精确路径后使用正常 git add，核对缓存差异和校验终态再提交。任何外部 capture readiness、START、hold 或 release 都必须来自单独明确的协调消息，索引交接不产生这些动作。

清单在每批和最终验收时按当前首方文件重新计算。新增文件及已审文件的内容变化均使正式清单重置为小写 `pending`；阶段审查包只授予实际闭合单元的信用，不能把少量入口或代表调用点扩大成整个头文件、模块或仓库完成。

# 调用链审查与注释规范

## 范围与清单

审查首方产品代码、测试、脚本、构建配置和人工编写的测试样例。第三方子模块、依赖副本、生成产物、二进制文件、锁文件和纯快照数据不作为注释对象。JSON 等不允许注释的格式仍需审查其配置或消费关系；结论写入台账或相关文档。归档目录中的首方源码也在范围内，是否仍参与构建必须逐文件核对当前构建配置。

以当前工作树中的已跟踪及未跟踪文件建立文件清单；每批开始与全仓结束时重新扫描，新增首方文件不得遗漏。记录文件归属、是否由其他活跃会话修改，以及审查状态。工作区原有差异不属于本任务，不能随注释提交。

`scripts/code_review_inventory.py sync` 根据 Git 文件列表更新 `inventory.tsv`，用 `sha256` 记录审查时的文件内容；内容变化会将该行重置为 `pending`，未变化则保留既有 `status` 和 `note`。`check` 核对清单是否与当前工作树一致，最终验收使用 `check --require-complete`，还会核对已审文件至少有一条格式正确的逐单元台账记录。文件级状态只用 `pending` 与 `reviewed`，仅在该文件的全部适用单元均有台账结论后改为 `reviewed`；脚本无法单凭清单证明没有遗漏函数，仍需独立审查者核对定义与台账。活跃会话的文件归属记录在会话协调说明与清单 `note` 中；归属释放前可只读审查，不写注释。

审查单元包括每个函数、可调用宏、公开接口、结构或类型定义，以及承载独立契约的全局状态。逐个阅读函数内的语句块；当某个块有跨层意图、隐含不变量或具体风险时，单独登记该块。普通局部控制块的审查结论随所属函数记录，不按花括号数量制造重复台账行。

## 从调用方还原意图

1. 从声明、实现和构建入口定位单元，搜索全仓直接调用及数据结构的构造、读写、转移、释放位置。
2. 追踪函数指针、回调注册、宏展开、生成代码、命令或测试入口，以及 C、Rust、TypeScript、WASM 等跨语言边界。文本搜索无结果不能证明死代码。
3. 向上追到用户可观察入口，向下查关键依赖和失败路径；核对调用前提、结果归属、有效期、线程/异步顺序及失败后状态。
4. 用当前源码、构建配置和测试相互印证。历史计划和模块文档只作线索；与当前调用路径矛盾时，先记录疑点再下结论。
5. 对每个单元给出明确结论：需要注释、无需注释、待核实或已证实缺陷。无法确定的契约不能写成事实。

## 注释内容和位置

新注释以中文为主，保留 API 名、协议名与 `TODO:`、`BUG:` 标签。已有准确注释无需机械重写。注释解释职责及调用目的，按需补充前置条件、资源所有权与有效期、失败语义、线程/时序限制、设计取舍和调用链意图；不逐句复述实现，也不在每处硬编码完整调用方清单。

- C 公开声明使用 `/** ... */` Doxygen；`@brief` 说明对调用方的作用，`@pre`、`@return`、`@note` 仅在存在相应契约时使用。调用约束优先写在声明处，内部实现只解释非显然的原因或不变量。
- TypeScript/JavaScript 导出接口使用 JSDoc；Rust 公开接口使用 `///`，不安全边界按 Rust 惯例使用 `// SAFETY:`；Python、脚本和 CMake 使用各自语言的行注释。
- 数据结构说明状态不变量、字段之间的关系、所有权或 ABI 限制。关键语句块说明为何必须采取该顺序、检查或回退。测试注释说明场景与防止的退化，而非重复断言。
- 示例和快照若会因注释改变解析或期望结果，只在台账中记录结论，不为追求注释数量修改它们。

`BUG:` 仅用于已复现，或经完整可达调用路径证明的缺陷；同处写明触发条件、可观察影响及复现测试或证据。`TODO:` 用于仍需确认的契约或风险；同处写明疑点、已知证据和下一步核查入口。推测性缺陷不得标为 `BUG:`。标签放在最贴近问题的源码或文档处，并在台账中保留完整证据。发现问题不在本任务内改变程序行为。

## 台账格式

每个功能模块在 `coverage/` 放置 UTF-8 TSV，首行固定为：

`file	unit	kind	callers	intent	constraints	evidence	decision	reason`

`file` 用仓库相对路径；`unit` 用可检索的限定名，语句块另附所属函数和用途；`kind` 标识函数、类型、宏、状态或语句块。`callers` 列列出直接调用者及已查明的间接入口；`evidence` 列列出当前实现、测试、构建或复现路径。`decision` 只使用 `commented`、`no-comment`、`TODO`、`BUG`。`no-comment` 必须在 `reason` 中说明为何现有名称或注释已足够。字段内用分号分隔多个值，不插入制表符或换行。

每个模块结束时核对台账与定义清单，确认没有未登记的审查单元；抽查调用点、注释和证据仍与当前工作树一致。若模块文档因此失真，依照文档现有的 `related_code`、`implementation_files`、`plan_sources` 和 `tests` 头部同步修正。

## 分工、验证与提交

多位 subagents 可并行进行只读调用链调查；写注释时每个文件只有一名负责者。独立 reviewer 核对注释是否从当前调用证据得出，是否遗漏单元或误用问题标签。活跃 SSA、LSP 等会话拥有的文件只读审查，待文件归属释放后再写入。

每个功能模块单独验收和提交。提交前运行 `git diff --cached --check`，检查暂存文件与完整差异，执行受影响模块的现有构建和测试，并与修改前基线比较。只暂存本任务的注释、台账及必要文档更正；不能安全拆分的原有差异继续延后。注释工作不添加只重复实现的测试，也不把已存在的测试失败描述为本任务修复成果。

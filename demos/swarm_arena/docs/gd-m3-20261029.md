## W10

`probes/w10_boundary` calls the same bounded `add_i64`, `noise2` and `nop`
operations through script functions, `zrgame.host`, `native extern`, and
dynamic `zr.ffi`. The dynamic path uses `loadLibrary`, `getSymbol` and
`SymbolHandle.call`. Library/symbol setup is cached outside timing; each dynamic
call builds its public API argument array inside timing. A separate process
closes the library twice, then must reject a symbol call with the exact closed
owner error and exit 1. This negative control is checked by the runner; CTest
itself is not inverted. The provider's fatal LoadError bypasses guest `catch`.

`tools/run_w10.py` validates twelve distinct checksum rows per run. It compiles
and deletes every script before binary execution, checks the execution-mode
marker, pins to CPU 5 when permitted, retains raw logs and binary identities,
and emits `result.json` plus `w10.md`. Timings are raw loop ns/call, including
loop/checksum work, with no baseline subtraction. `nop` checks completion count;
the other operations verify numeric results in the script and runner.

The descriptive baseline uses 20,000 measured calls, 1,000 warmup calls per
operation/path and three fresh-process repetitions per mode. Load above 2.0
disqualifies regression claims. See the checked-in
[W10 table](perf-gd-m3-20261029.md) and the external report for measured rows.
The two W10 CTests use 2,000 calls and one repetition as correctness gates.

The native host descriptor is now `1.1.0` / `zrgame.host:v2`, with `addI64`,
`noise2` and `nop` matching the existing FFI fixture. No engine changes are
included.

## Pool attempt and hard stop

P11's successful struct deliver/borrow/read/recycle test was the starting
point. The attempted lane implemented `Pool<EnemyData>`, a dense handle order,
stable-ID lookup, weak `PoolHandle` bullet targets, stale-target ballistic
fallback and `BufferPool.rent<int>` neighbour scratch. A standalone source
check passed identity, writeback, slot reuse, homing, bullet swap removal,
scratch return/reuse and shutdown assertions.

The integrated lane could not be made reliable within the demo scope:

- Splitting native generics across script modules produced incompatible
  `PoolHandle<EnemyData>`, `PoolHandle<world.EnemyData>` and qualified spellings.
  Consolidation avoided that diagnostic, but the fuller repeated-import
  composition lost class method bindings. A smaller stripped control passed,
  so this is not a claim that every repeated import fails.
- Module-local factories allowed an observed two-frame CLI/host source pair
  to pass. A prototype CLI completed 120 frames with hash `737368736`, versus
  DOD's `552988638`. That prototype did not yet hash homing target state and is
  not an accepted Pool golden. The later target-aware variant did not complete
  integration. The attempted ballistic control failed during boot; it provides
  no evidence of hash parity.
- The Pool project compiled, then failed source-removed binary execution with
  `import_load_unavailable: module 'lanes/pool/world'` and
  `loader=binary-runtime result=load-failed`. Eagerly importing it also broke
  the DOD binary smoke.
- Lazy selection protected DOD binary loading, but object/cast dispatch lost
  session members or receiver fields (`booted`, `tick`, `shutdown`). Qualifying
  native guard types produced another type-identity diagnostic.

Under the requested hard stop, the attempted lane and selector changes were
removed from the product tree. No failed verification was inverted or marked
passing; no golden was regenerated. Default selectors, simulation and existing
tests are restored. W5 is unmeasured, Pool/DOD parity is not achieved, and no
Pool performance, binary, sanitizer or forced-GC acceptance is claimed.

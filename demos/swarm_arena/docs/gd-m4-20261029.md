# GD-M4 partial delivery — 2026-10-29

Trace stripping and CLI Job spawning are accepted in interpreter and
source-removed binary modes. Reflection-backed tunables are **blocked**;
there is no accepted tunables dump or validation path.

## Trace and profiles

`game/swarm_arena.zrp` declares `trace` and debug/release `build.profiles`.
The default manifest leaves this feature disabled. `traceStart` in the CLI
entry uses `#zr.compile.conditional("trace")#` and logs the scenario and
configured frame count when enabled.

The stock loader consumes `build.features` declarations and the top-level
boolean `features` map. It does not select `build.profiles`, and CLI `--profile`
means runtime profiling. The demo's `tools/run_m4.py --stage-profile` copies
the project and projects the selected profile's `enableFeatures` into that
boolean map. It does not rewrite script source. Thus profile selection is a
demo tooling capability, not a newly implemented engine capability.

`demo_m4_trace_interp` and `demo_m4_trace_binary` stage both profiles, run the
canonical 120-frame smoke, and require the retained simulation/state golden.
They invoke `--dump-bytecode` for the actual game entry and an argument-side-
effect control (`game/tools/trace_arguments.zr`). The CLI dumps only the entry
function, so both calls under inspection are deliberately in their entries.
The check finds the call's source line and compares its opcode sequence to
`goldens/trace.json`; paths, register operands and offsets are excluded.

Debug retains the trace call and evaluates the control argument once. Release
has zero instructions for both conditional call expressions, no trace output,
and zero argument evaluations. These are call-stripping results; removal of
the trace function's definition or string constants is not claimed. Binary
checks compile each profile separately, delete every copied `.zr` (including
packages, tests and tools), then run a fresh process. Raw dumps, commands and
artifact hashes are retained by the runner. The new opcode golden was captured
from these observed positive/negative controls on base `378f2cdd`; existing
simulation goldens were not changed.

## Director Jobs

CLI `--spawn-mode direct|jobs` selects the shared Session's director path;
direct remains the default. The Job path creates a cold `Job<int>` containing
the director update, submits it through `task.currentScheduler.schedule<int>`,
then collects the Task with `.result()` during the spawn phase. The result is
the batch size; the same ordered SoA requests feed the existing spawn loop.
No other phase consumes the RNG between scheduling and collecting the result.

The native cooperative scheduler eagerly pumps its queue during `schedule()`
unless already pumping. This path therefore demonstrates Job submission,
queue reuse and completion collection; it provides no worker parallelism or
deferred-until-result execution. Tasks stay in a local variable: the attempted
field assignment was rejected as `Task values must be awaited, returned, or
stored`. The callable's target method precedes it in the class, and the
scheduler import is local to the method to satisfy current compiler binding.

`demo_m4_jobs_interp` and `demo_m4_jobs_binary` check ordered request columns
and RNG equality over 120 director updates, reject two outstanding batches
and duplicate collection, and cover empty batches plus the boss burst. They
then compare direct/Job simulation hashes, checkpoint 60, every deterministic
success field, and render hashes for seven cases:

- smoke: 120 frames/seed 12345, 61 frames/seed 1, 1 frame/seed 2147483646;
- arena_2k, swarm_10k, bullet_storm and particle_burst: four frames/seed 12345.

Existing goldens gate the canonical smoke and the four short scenarios. The
canonical Job run schedules/drains 120 Jobs, creates 271 spawn requests, and
retains hash **552988638**, checkpoint **42922906**. The runner requires the
Job counters; silently falling back to direct spawning cannot pass. Bad mode
selection must exit 2 with the normal cleanup marker. The host CLI does not
expose this selector; host default DOD/C regression checks remain applicable.
Long non-smoke Job runs, per-frame full-game parity, sanitizer and forced-GC
acceptance are not claimed by this milestone.

## Tunables hard stop

The original P19 probe fails at `import("zr.reflection")` in both execution
modes with `import_load_unavailable: module 'zr.reflection'`. Compilation
succeeds; its binary failure also reproduces with source loading disabled.

An additional `ScenarioConfig` struct with seven numeric fields and
`#Tunable(min: ..., max: ...)#` attributes, runtime field retention, field
enumeration and retained-attribute checks also compiles. It fails at the same
runtime import before enumeration. A second copy with every script deleted
retains the failure. Consequently reflection validation and a real tunables
dump cannot be accepted. The attempted sources are preserved outside the
product tree; no handwritten dump is substituted for reflection and no
tunables golden is invented. Production Config and existing P19 expected-
failure checks retain their prior contract. No engine changes are included.
